### 4.2 回测结论（2026-06-25 ~ 09-22，共 80 天，已修正前视偏差）

回测脚本：`scripts/backtest-funding.py`（参数可用环境变量覆盖，便于敏感性分析）。

费率已换成账户真实值（现货 0.06% / 合约 0.0375%，年化成本 1.58%）：

| 池门槛 | 建仓门槛 | 换仓差 | 持仓数 | 年化 | 调仓次数 |
| --- | --- | --- | --- | --- | --- |
| 500 万 | 5% | 4 个点 | 3 | **11.27%** | 9 |
| 500 万 | 8% | 4 个点 | 3 | **22.12%** | 8 |
| 500 万 | 5% | 4 个点 | 1 | 22.04% | 8 |
| 2000 万 | 5% | 4 个点 | 3 | 3.69% | 11 |
| 2000 万 | 8% | 4 个点 | 3 | 3.68% | 5 |
| 500 万 | 5% | 近乎无滞回（0.01 个点） | 3 | 8.64% | 17 |

**三个结论**：

1. **换仓滞回非常重要**。4 个点滞回下 80 天只调仓 8~11 次，年化 11%~22%；换成近乎无滞回要调仓 17 次，年化掉到 8.64%。
2. **门槛卡在 2000 万，做不到 8%**（只有 3.7%）；放到 **500 万**，年化 11%~22%，能覆盖 8% 目标。所以默认门槛定为 500 万。
3. **集中比分散赚得多**。持仓 1 个币 22.04%，3 个币 11.27%（按成交额加权会被里面收益率最低的币拖累）。上限仍保留 3 个，但"不足则少持"这条要保留。

**注意一个数据陷阱（2026-09-23 补充）**：建仓门槛一提高，达标币就变少，组合会**自动变成单币集中**，"最多 3 个"根本用不上。实测：

| 建仓门槛 | 实际平均持仓数 | 年化 |
| --- | --- | --- |
| 5% | 3.00 个 | 11.27% |
| 6% | 3.00 个 | 11.27% |
| 7% | 3.00 个 | 11.27% |
| 8% | **0.97 个**（80 天里 78 天只持有 1 个币） | 22.12% |
| 10% | 1.85 个 | 18.28% |

所以"把门槛提到 8% 收益最高（22.12%）"不是"兼顾了分散投资"，恰恰相反——它是**单币集中**的结果，而且年化随门槛非单调（5~7% 是 11.27%，8% 跳到 22.12%，10% 又回落到 18.28%），说明这个数字高度依赖样本、不具备稳健性。

**建议维持建仓门槛 5%**（5~7% 都一样），持有 3 个币拿到 11.27%，已经超过 8% 目标，且是真正分散的。

### 4.3 我的建议（当时提出，部分已被后续结论取代，最终以 4.5 定稿为准）

1. **先解决滑点，再决定池门槛**。≥500 万那一档回测能到 8~19%，但那些币的滑点未知；"2000 万"这个门槛是否合理，取决于滑点能不能量化。建议下一步用盘口深度估一次滑点，把成本模型从"固定 2.60%"换成"按币计算"。→ **已完成**，见 5.1。
2. **换仓差保持 4 个点**，这是回测里最有效的参数。→ 已采纳。
3. **持仓数改成"按质量决定、上限 3"**，而不是固定 3 个。→ 已采纳。
4. **建仓门槛 5% 与 8% 差别不大**，可以先取 5%，给策略留下观察期。→ 已采纳。

### 4.4 恢复轮数过滤的实现与效果（2026-09-23 完成）

2. 再看该币**当前连续为正的轮数**；

## 5. 模块 4：策略与调仓（已完成）

**目标**：把"该持有哪个币"变成一个具体可执行的持仓方案——每个币投多少钱、怎么建仓、怎么平仓、钱不够时怎么办。

**待确认问题（第一批）**：

1. **仓位规模**：总资金里拿多少比例投入？每个币平均分配，还是按净年化加权？单币仓位上限设多少（比如不超过总资金的 40%）？
2. **合约腿杠杆**：永续空仓用几倍杠杆？这直接决定占用多少保证金、以及强平风险。
3. **建仓执行顺序**：先买现货再开空，还是先开空再买现货，还是同时下单？中间那几秒会有方向暴露。
4. **下单方式**：用市价单（快，吃单费率 0.06%/0.0375%）还是限价单（省手续费，但可能挂不上、腿对不齐）？
5. **一次建满还是分批**：直接按目标仓位一次建好，还是分 2~3 批？
6. **闲置资金**：空仓或部分持仓时，剩余资金放在哪（账户余额 / 理财）？
7. **权重再平衡**：3 个币按成交额加权的权重，多久调整一次？还是只在换仓时顺带调整？

### 5.2 我的建议方案（供你决策）

**① 仓位规模**

- 建议：单币上限 **40%** 总资金；按净年化排序取前 3 个，权重先按成交额加权（沿用模块 3 的规则）。
- 收益/风险：集中度越高收益越高、单币风险越大。40% 上限意味着最坏情况下单币归零也只损失 40%。
- 备选：按净年化加权（收益略高、风险更集中）。

**② 合约腿杠杆**

- 建议：**1~2 倍**。delta 中性的收益来自资金费，不来自杠杆；杠杆只放大强平风险。
- 关键点：UTA 统一账户里现货和合约共用保证金，现货资产本身也能充当保证金，所以"现货全额 + 合约 1 倍"的资金效率已经很高，没必要加杠杆。
- 风险：杠杆超过 3 倍时，小币的极端行情可能触发强平，反而把"无风险套利"做成有风险。

**③ 建仓顺序**

- 建议：**两条腿同时发起**，下单前先取好盘口、算好数量。
- 理由：先买现货则中间几秒是净多头，先开空则是净空头，都有方向暴露；同时发起把暴露时间压到最短。
- 兜底：若一条腿成交、另一条腿失败（拒单/深度不足），立即用市价单补另一条腿，并记录告警。

**④ 下单方式 + 下单量（回应你的提议）**

- 建议：**吃单价**（市价单或可立即成交的 IOC 限价单）。对冲要求两条腿必须都成交，挂单等成交会造成单边暴露。
- **下单量由盘口深度决定**（你的提议，采纳）：
  1. 下单前取订单簿；
  2. 从最优价开始累加，算出"在滑点上限内能吃多少量"；
  3. 滑点上限建议：主流币 **0.05%**、小币 **0.15%**（每条腿）；
  4. 若该币在最小可交易金额（如 5k）下都超上限，**直接放弃这个币**。
- 数据支撑：20k 单笔时，MUBARAK 单边滑点 0.81% 远超上限 → 该币只能拆到 5k 以下甚至放弃；NEAR 0.13% 可接受。

**⑤ 一次建满还是分批**

- 建议：**分批**，按盘口深度切成 2~4 批，每批间隔几秒；每批内部两条腿同时下。
- 收益/风险：分批能压低滑点，但拉长了单边暴露时间。建议只在"目标金额超过盘口可承受量"时才分批。

**⑥ 闲置资金**

- 建议：放账户余额（活期），**不要买理财/质押**——那些产品有赎回周期（T+N），换仓时可能取不出来。
- 收益影响：空仓期资金收益率为 0，这会拉低整体年化；如果长期空仓，可以考虑国债逆回购这类随时可取的品种，但优先级低于"随时能调仓"。

**⑦ 权重再平衡**

- 建议：**不单独做再平衡**，只在换仓时顺带调整到目标权重；并加一条阈值，偏离目标超过 20% 才动。
- 理由：再平衡本身要交易，每次交易都是成本；而权重偏移对收益的影响远小于交易成本。

**⑧ 参考基线（把上面八条合起来）**

> 总资金分 3 份，单币上限 40%；合约腿 1 倍杠杆；下单前查盘口，按滑点上限（主流 0.05% / 小币 0.15%）算出可下单量，超出则分批；两条腿同时下、用吃单价；闲置资金放余额；只在换仓时调整权重。

（✅ 在滑点上限内、⚠️ 需分批、❌ 明显超限）

**结论**：

1. **初期（20 万 RMB）单笔基本没有风险**——主流币和大半中等币都在上限内，只有 FARTCOIN / MUBARAK / WIF 这类最薄的币会被规则自动排除或拆单。所以"单笔不会有太大风险"这个判断，在你的资金量级下是成立的。
2. **但资金涨到 200 万 RMB 时情况会变**：单币 11 万 USDT，连 DOGE、HYPE 都要分批，小币直接不可做。**这也是为什么"下单量由盘口决定"必须写死在代码里，而不是靠人工判断**——资金规模一变，可做的币种就变了。
3. 好消息是：这套规则会**自动适应**。资金小的时候多做小币（收益高），资金大了自动退回到大币（收益低但能容纳）——收益随规模下降是正常的，不是 bug。

### 6.1 建议方案（待确认）

**贯穿原则**：资金费是慢变量（4~8 小时结算一次），我们对速度没有要求。所以一切选择都偏向**确定性**和**可回滚**，而不是"快"；任何"为了成交而加大风险"的选项（超时转市价、加仓追平）都排除；每个分支的最坏结果必须是"少赚"，不能是"亏"。

**① 成交回报：先轮询，不上 WebSocket**

- 建议：轮询 `order-info`，间隔 1 秒，直到成交或超时。
- 理由：一次只涉及 2~3 笔订单，REST 限频 20 次/秒/UID 绰绰有余；WebSocket 要额外处理断线重连、丢包、订阅恢复，引入的故障模式比它解决的问题多。秒级延迟对 4~8 小时结算的策略毫无影响。
- 后续：实盘稳定后如果确有需要，再上 WebSocket。

**② 部分成交：用 IOC 限价单从根上规避**

- 建议：下单用 **IOC 限价单**（限价 = 盘口可承受范围的边界价），要么全部成交、要么整笔取消，不会出现"半仓"。万一仍出现部分成交，撤掉剩余、重新取盘口再下，最多重下 2 次。
- 理由：市价单可能部分成交，留下单边敞口，处理起来更麻烦。IOC 限价同时还能兜住滑点，比裸市价更稳。

**③ 超时：10 秒（不是 30 秒）**

- 建议：10 秒未成交判超时 → 撤单 → 重新取盘口 → 重下；连续 2 次超时就**放弃这一批**并告警。
- 理由：我们是按盘口深度定量的，正常 1~2 秒就该吃完；10 秒还没成说明盘口已经变了。
- **明确不做**：超时直接转市价。大额市价滑点不可控，违背"不亏本"的底线。

**④ 两腿偏差：容差 0.5%，兜底方向永远是"减到对齐"**

- 建议：两条腿名义价值偏差 ≤ 0.5% 视为合格；超出先补小的那条腿；**补不齐（深度不足）就把大的那条腿减到与小的匹配**，并告警。
- 理由：delta 中性要求两腿相等，未对冲的部分就是纯投机。**兜底永远是减仓，不是加仓**——减仓最坏是少赚，加仓可能多亏。

**⑤ 幂等 ID：用可复现规则，不用随机串**

- 建议：`q{策略仓位ID}-{腿}-{批次号}`，例如 `q12-spot-1`、`q12-perp-1`。
- 理由：官方明确说合约减仓单冲突时 `orderId` 会返回 null，只能靠 `clientOid` 兜底。可复现的 ID 让程序重启后也能判断"这笔单是不是我已经下过的"，随机串做不到。
- 约束：官方要求 `^[0-9A-Za-z_:#\-\+\s]{1,32}$`，本格式符合。

**⑥ 告警：先日志 + 后台异常列表，关键事件用 ERROR 级**

- 建议：一期不引外部告警渠道；但**下单失败 / 两腿不平 / 超时放弃 / 保证金告警**必须同时做到"ERROR 级日志 + 写入后台异常列表 + 看板显眼展示"。服务器上线后再接 Telegram / 邮件，且**只发事件描述，绝不发密钥**。
- 理由：一期避免引入外部依赖，同时保证关键异常不会被淹没在日志里。

### 7.1 先澄清：现货全额对冲为什么仍可能被强平（2026-09-23）

常见疑问："我持有同等数量的现货，价格怎么涨都有现货对应，怎么会强平？"

答案：**在统一账户里现货确实能充当合约的担保品，单纯价格涨跌不会爆仓**（现货端浮盈顶上合约端浮亏）。但有三点会让这句话打折：

1. **保证金折扣率（haircut）**：现货不是 100% 计入保证金。实测 511 个币（`/api/v3/market/discount-rate`）：

   | 币种 | 折扣率 |
   | --- | --- |
   | BTC / ETH | 0.98 |
   | ADA / DOGE / SOL / XRP / HYPE | 0.95 |
   | NEAR / SUI | 0.90 |
   | TAO / GRASS | 0.80 |
   | PONS / WIF | 0.60 |
   | MUBARAK | **0.10** |

   全市场分布：**116 个币的折扣率只有 0.10**，133 个是 0.60。以 MUBARAK 为例，1 万美元现货只能算 1,000 美元保证金，合约端浮亏超过这个数就可能被强平。
2. **ADL（自动减仓）**：极端行情下交易所会强制平掉盈利方仓位，可能把我们的空仓平掉，留下裸现货。
3. **下架 / 交割**：币种下架会强制平合约仓位，同样留下裸现货。

另外**标记价与现货价的瞬时偏离**（插针）也会放大风险：合约端按标记价算亏损、现货端按现货价算浮盈，两者不同步。

**因此新增一条币种准入条件：保证金折扣率 ≥ 0.8**（按实测值，TAO / GRASS 可进，PONS / WIF / MUBARAK 被排除）。

#### 强平到底需要涨多少？（推导 + 实测参数）

统一账户里的强平条件是"担保价值 − 浮亏 < 维持保证金要求"，其中：

- 担保价值 ≈ **折扣率 d** × 现货市值（现货涨 1%，担保只按 d 计入）
- 合约浮亏 = 名义价值 × 涨幅 r（**全额计入，不打折**）
- 维持保证金要求 = **维持保证金率 m** × 合约名义价值

解出触发强平所需的涨幅：**r > (d − m) / (1 + m − d)**

代入实测参数（持仓档位接口返回的 `mmr`：ETH 0.4%、WIF 1.5%、MUBARAK 2%）：

| 币种 | 折扣率 d | 维持保证金率 m | 触发强平所需涨幅 |
| --- | --- | --- | --- |
| BTC / ETH | 0.98 | 0.4% | **约 41 倍（+4070%）** |
| SOL / XRP / DOGE | 0.95 | 0.5%~1% | 约 16~32 倍 |
| NEAR / SUI | 0.90 | 约 1% | 约 8 倍 |
| TAO / GRASS | 0.80 | 1.5%~2% | **约 3.6 倍** |
| WIF / PONS | 0.60 | 1.5%~2% | 约 1.4 倍（+140%） |
| MUBARAK | 0.10 | 2% | **+8.7%** |

**两个结论**：

1. "折扣率 0.8 → 现货涨 20% 就爆仓"**不成立**，实际要约 3.6 倍。因为维持保证金只要 1.5% 左右，而现货提供了 80% 的担保，缓冲很大；折扣率只是让每 1% 的涨幅"漏掉" 20%。
2. 真正危险的是**折扣率 0.1~0.6 的币**：116 个币涨 9% 就爆，133 个币涨 140% 就爆。所以把关口设在**币种准入（折扣率）**上最有效，而不是靠事后兜底。

#### 算例：折扣率 0.8、现货 100、空头 100，涨 81% 会爆仓吗？

**不会。** 常见的误解是把担保价值"冻结"在开仓时（80），但**现货涨了之后担保价值也一起涨**：

| 项目 | 涨 81% 后 |
| --- | --- |
| 现货市值 | 100 × 1.81 = **181** |
| 现货担保价值 | 181 × 0.8 = **144.8** |
| 合约浮亏 | 100 × 0.81 = **81** |
| 账户权益 | 144.8 − 81 = **63.8** |
| 维持保证金要求（按 2%） | 181 × 2% = **3.6** |

权益 63.8 远大于要求 3.6，不爆仓。换个角度看更清楚：**现货赚的 81 和合约亏的 81 两两抵消**，唯一损耗是"现货赚的那 81 只按 80% 计入担保"，即漏掉 16.2；担保从 80 降到 63.8，离爆仓线还远。

**每涨 1%，只漏掉 (1 − 折扣率) = 0.2% 的担保；初始缓冲有 (折扣率 − 维持保证金率) = 78%。** 所以触发爆仓的涨幅 ≈ 78% ÷ 0.22% ≈ **354%（涨约 3.5 倍）**，与公式一致。

#### 关键澄清：强平 ≠ 亏光，也 ≠ 此刻是赚的

Bitget 的两个字段含义不同（官方定义）：

- `accountEquity` **账户总权益** = 真实净值
- `effEquity` **有效权益** = **打折后**可用于保证金的净值（"账户中可为全仓模式下的现货、永续合约交易提供保证金的资产折合成法币价值的净值"）

**强平触发看的是 `effEquity`，不是真实净值。** 用上面的例子（折扣率 0.8、现货 100、空头 100、涨 354%）：

| 项目 | 数值 |
| --- | --- |
| 现货市值 | 100 × 4.54 = **454** |
| 合约浮亏 | 100 × 3.54 = **354** |
| **真实净值** | 454 − 354 = **100（基本持平）** |
| **有效权益（打折后）** | 454 × 0.8 − 354 = **9.2 ← 强平在此触发** |

结论：**被强平不是因为亏光了钱，而是"打折后的保证金资格"不够**。真实净值那一刻约等于持平，扣掉清算费用后是**略亏**——所以"爆仓那一刻大概率是赚的"不成立。

还有一个方向性判断需要纠正：**强平你的那种行情几乎都是空头挤压**——价格暴涨→空头被强平→强平单本身是市价买入→继续推高价格。也就是说，**这波暴涨的燃料正是你的强平单**；等被迫买入结束，推动力消失，挤压后回撤是更常见的形态。所以"强平后拿着现货等它继续涨"是**胜率不占优的方向赌注**，与"不亏本"的铁律冲突。

**因此明确：不设"强平后持有等待"模式。** 检测到强平 / ADL 后立即市价卖掉现货腿并熔断——尾部事件的处理原则是止损离场，不是加大赌注。

| 对账频率 | 持仓与权益**每 5 秒**（与风控共用同一次轮询，不额外消耗）；未成交订单与成交明细每分钟；财务流水每小时 |

| 差异处理 | 分级：可自动修正的（如数量小数位差异）自动修正并留痕；必须熔断告警的（持仓方向不符、凭空多出一条腿）立即熔断 |
| 资金费对账 | 用 `account_financial_record`（真实到账）与本地记录核对，超出容忍度（手续费与舍入误差）就告警 |
| 停机补录 | 启动后按缺口补采，历史费率接口 90 天足够覆盖 |
| 对账留痕 | **每次对账的结果与差异都落库**，便于事后追溯 |

## 9. 模块 8：盈亏核算（已定稿）

**目标**：把"到底赚了多少、钱赚在哪、成本花在哪"算准并展示出来。后台看板的数据全部来自这一层。

**待确认问题（第一批）**：

1. **净值曲线用哪个口径**：直接用交易所的 `accountEquity`（真实净值，含未实现盈亏），还是我们自己按策略口径重算？建议**两个都展示**：交易所口径用来对账，策略口径用来评估。
2. **成本怎么归集**：手续费（来自成交明细）、滑点（成交价 vs 下单前盘口最优价）、换仓频次，分别记到什么粒度？建议**按"每笔成交"记原始值，按"每次换仓"汇总**，看板上能下钻。
3. **资金费收入以谁为准**：以交易所真实流水为准（`account_financial_record`），还是以理论值（费率 × 仓位 × 结算点）为准？建议**以真实流水为准，理论值只作对照**——差异本身是很有价值的信号（说明我们的模拟或口径有偏差）。
4. **已实现 / 未实现怎么切**：换仓平掉那一刻，把这一组仓位的资金费收入、手续费、滑点、基差变化一起结算成"这一组赚了多少"？
5. **年化怎么展示**：滚动 7 天 / 30 天 / 90 天 / 累计？含成本还是纯资金费？建议默认展示**含成本、滚动 30 天**，其余可选。
6. **归因粒度**：能不能看出"这个币赚了多少、成本花了多少"？建议做到**单币 + 组合两级**。
7. **基准对比**：要不要跟"闲钱放活期"做个对比（体现策略到底创造了多少超额收益）？

### 9.1 模块 8 定稿（非核心模块，按建议直接采用，你可随时改）

| 决策项 | 结论 |
| --- | --- |
| 净值口径 | **两个都展示**：交易所 `accountEquity`（真实净值，用于对账）+ 自算策略口径（用于评估业绩） |
| 成本归集 | 手续费与滑点**按每笔成交记原始值**，**按每次换仓汇总**；看板可下钻 |
| 滑点定义 | 成交价 vs 下单前盘口最优价的偏移（与 `scripts/orderbook-slippage.py` 同一口径） |
| 资金费口径 | **以交易所真实流水（`account_financial_record`）为准**，理论值只作对照；两者差异单独展示（差异是校准信号） |
| 已实现 / 未实现 | 以**一组策略仓位**为单位结算：平仓时把该组的资金费、手续费、滑点、基差变化一起结出"这组净赚多少" |
| 年化展示 | 默认**含成本、滚动 30 天**；另提供 7 天 / 90 天 / 累计 |
| 归因粒度 | **单币 + 组合两级** |
| 基准对比 | 加一条"闲钱活期"基准线，体现超额收益 |

## 10. 模块 9：模拟交易（已定稿）

**目标**：不上真钱，用完整程序跑一遍策略，验证"收益能否达到 8%"和"程序能否稳定运行"。

### 10.1 模块 9 定稿（非核心模块，按建议直接采用）

**两种模拟都做，但一期先做前瞻模拟（paper trading）：**

| 方式 | 说明 | 优先级 |
| --- | --- | --- |
| 历史回放 | 用已有 90 天数据跑规则（`scripts/backtest-funding.py` 已能给出方向性结论） | 已完成粗版，够用 |
| **前瞻模拟** | 程序按真实节奏运行（每小时评估），行情/费率走真实接口，**下单只在本地模拟** | **一期主做** |

**前瞻模拟的实现方式**（正好复用一期就定好的 `ExchangeGateway` 双实现）：

1. `MockExchangeGateway`：行情、费率、盘口读**真实接口**；下单 / 撤单 / 查单在本地模拟。
2. 成交价用**实测盘口深度**推算（复用 `scripts/orderbook-slippage.py` 的算法），而不是加一个固定滑点值。
3. 模拟成交写入 `trade_order` / `trade_fill`，`source = mock`——**与实盘共用同一套表和同一套核算**。
4. 资金费到账按结算点用真实费率 × 仓位计算，写入 `funding_income`，`source = mock`。
5. 其余模块（调度、对账、告警、盈亏）**与实盘完全共用**，这样模拟阶段就在验证真实程序。

**上实盘的门槛（退出条件）**：

- 连续运行 **≥ 3 个月**；
- 滚动年化（含成本）**≥ 8%**；
- 最大回撤 **≤ 5%**；
- 无未解释的对账差异，且熔断/告警事件都能解释。

### 10.2 重要更新：优先使用 Bitget 官方模拟盘（2026-09-23 查证）

**结论：不自建 mock 撮合，改用官方模拟盘。**

官方文档（`docs/uta/demo-trading/rest-api`、`demo-trading/websocket`）确认：

- **支持 API 交易**：接口地址不变（`api.bitget.com`），只需在请求头加 `paptrading: 1`；
- 需要**模拟盘专用 API Key**（登录 → 切换至模拟盘 → 个人中心 → API Key 管理创建），前提是账号**已通过 KYC**；
- WebSocket 走模拟盘专用地址：公共 `wss://wspap.bitget.com/v3/ws/public`、私有 `wss://wspap.bitget.com/v3/ws/private`；
- 官方定位即"用虚拟资金在**实时市场环境**练习交易、测试策略"。

**为什么比自建 mock 好**：行情、费率、下单、成交、持仓、账户全走真实链路，**只有资金是虚拟的**。自建撮合等于自己重写一遍撮合逻辑，而部分成交、滑点、拒单、强平等真实行为复现不出来，模拟结果可能与实盘差很远。用官方模拟盘，跑的就是真实代码路径，对账与风控模块能一起验证。

**模拟盘实测结果（2026-09-23/24 已全部验证）**：

| 待验证项 | 结果 |
| --- | --- |
| 1. 现货与 U 本位永续是否都支持下单 | ✅ 都支持（且公开产品接口加 `paptrading:1` 头即可拿到模拟盘清单，无需签名） |
| 2. 资金费是否真实结算 | ✅ **会结算**：2026-09-24 08:00 到账 +0.4749 USDT（类型 `CONTRACT_MAIN_SETTLE_FEE_USER_IN`）→ **模块 9 不需要自己 mock 资金费** |
| 3. 限频是否与实盘一致 | ⏳ 未测（当前调用频率远低于限频，暂不影响） |

**但发现两个关键限制**：

1. **金额口径不可信**：实得 0.4749 USDT，而按"名义 18,958 × 汇率 0.000068"应得 1.289 USDT，差 2.7 倍
   → 模拟盘的资金费**金额**不能用来校验策略收益，收益验证仍需自建 mock。
2. **覆盖与报价问题**：只支持 BTC/ETH/DOGE/SOL，其中 **ETH、SOL 的现货报价是坏的**
   （ETH 卖一 54500 而市价 2726），且**限价偏离市价超 2% 直接被拒** → 实际只能拿 BTC 跑流程。

**配置方式**：模拟盘 key 与实盘 key **分开**，同样只放仓库外的 `~/.quantification/application-local.yml`；代码里加 `bitget.paptrading` 开关，为 true 时给所有请求带上 `paptrading: 1` 头。

**兜底原则**：模拟盘缺什么补什么——下单走模拟盘，缺失的能力（如资金费结算）由我们自己按真实数据记账。

### 10.3 模拟盘实测结果（2026-09-23）

用已创建的模拟盘 key 实测：

| 检查项 | 结果 |
| --- | --- |
| 模拟盘 key 可用 | ✅ 环境独立（独立 userId 与账户，与实盘互不影响） |
| 交易权限 | ✅ `read_and_write` + `uta_trade`，可下单 |
| 支持现货 | ✅ 有现货费率与交易对配置 |
| 支持 U 本位合约 | ✅ 有合约费率与交易对配置 |
| **覆盖范围** | ⚠️ **很小**：现货 25 个（真币仅 BTC/ETH/XLM/DOGE/SOL/BGB/CRV）；合约 45 个（真币 18 个）；**两者交集只有 BTC / ETH / DOGE / SOL 四个** |
| 资金费是否结算 | ❓ 待验证（需要持仓过一个结算点；当前模拟盘余额为 0） |
| 限频是否与实盘一致 | ❓ 待验证 |

**这条限制很关键**：我们的目标池是成交额 ≥500 万的币（当前 57 个），而模拟盘只覆盖其中 **4 个**；收益最高的那批中小币（TAO / GRASS 等）模拟盘**完全不支持**。

**据此修正模块 9 的方案：官方模拟盘与自建 mock 两套并用，各解决一个问题。**

| 方案 | 覆盖 | 验证目标 |
| --- | --- | --- |
| **官方模拟盘** | BTC / ETH / DOGE / SOL 共 4 个币 | **程序链路是否稳定**：真实下单、成交、持仓、对账、重启接管、风控、告警 |
| **自建 mock** | 完整候选池（57 个币） | **策略收益是否达标**：行情/费率/盘口用真实数据，下单本地模拟并计入滑点 |

也就是说：**模拟盘验证"程序对不对"，自建 mock 验证"策略赚不赚"**。两者都不能省。

**当前两个待办**（需要用户操作）：

1. 在 `~/.quantification/application-local.yml` 的 `bitget:` 下补一行 **`paptrading: true`**（没有这行，程序默认走实盘）；
2. 在模拟盘界面领取虚拟资金（当前模拟盘账户余额为 0，需在 UI 里领取/重置后才能下单）。

### 10.4 重大发现：现货默认不计入保证金（2026-09-23 实测）

在模拟盘开了一个 delta 中性仓位（现货 BTC ≈2 万 USDT + 合约空 0.2337 BTC），账户数据：

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| `accountEquity` | 49,984 | 真实净值（含现货那 2 万） |
| `effEquity` | 29,952 | **有效权益只含 USDT，现货那 2 万完全没算进去** |
| `mmr` | 87.7 | 维持保证金 |
| `mgnRatio` | 0.0029 | 实测 = `mmr ÷ effEquity`（87.71 ÷ 29,952 = 0.0029，完全吻合）✓ |

查询抵押品设置：**`collateralType = custom`、`collateralCoins = USDT,USDC`** —— 只有 USDT/USDC 算抵押品。

尝试修改都失败：

- 查询参数方式 → `400172 参数校验失败`；
- JSON body 方式 → **`25125 当前模式不支持抵押品设置，请切换账户模式`**。

（平台的"自定义抵押品支持币种"清单里确实有 BTC / ETH / SOL / DOGE 等 14 个币，所以不是币种问题，而是**账户模式**问题；当前账户模式是 `hybrid`。）

#### 对策略的影响（重要，会影响收益结论）

1. 我先前推导"现货扣掉折扣后仍能充当保证金"的公式，**前提是抵押品模式允许该币种**。当前设置下，现货对保证金的贡献是 **0**。
2. 如果实盘也是这个设置，那么"现货全额 + 合约 1 倍"实际需要 **2 倍资金**（现货占用 1 份 + 合约保证金 1 份），**收益要按总占用资金折算 → 回测的 11.71% 会掉到约一半，达不到 8% 目标**。
3. 所以**必须先解决抵押品模式**（切到支持抵押品设置的模式，再把目标币种加入抵押品，或选 `mainstream` / `all`），否则整个收益模型不成立。

#### 处理方式（2026-09-23 决定）

**暂不切换账户模式。** 这条记为**待确认项**，等用真实资金前再验证（实盘账户的抵押品模式可能本来就不同）。

- **⚠️ 上实盘前必须核实这一项**：如果实盘也是"只认 USDT/USDC 作抵押品"，那收益要按 2 倍占用资金折算（11.71% → 约 5.9%），达不到 8% 目标，收益模型需要重算。
- 保证金安全线可以按 `mgnRatio = mmr ÷ effEquity` 这个口径定阈值（已实测确认）。
- **待验证**：资金费是否真实结算（已建仓，等 2026-09-24 00:00 的结算点）。

### 10.5 自建 mock 落地（2026-09-24，v1 已跑通）

**开关**：`simulation.enabled=true`。此时**行情 / 费率 / 盘口仍读真实接口**，
下单 / 撤单 / 查单走本地模拟撮合。`bitget.paptrading` 继续负责区分实盘与官方模拟盘，两道安全闸不变；
自建 mock 天然不动真实资金，因此不需要第二道闸（`MockExchangeGateway` **不注入**私有客户端，
从设计上就不可能发出真实交易请求）。

**代码结构**（新增 `com.quantification.exchange` 包）：

| 类 | 职责 |
| --- | --- |
| `ExchangeGateway` | 交易所网关接口：账户 / 持仓 / 费率 / 下单 / 撤单 / 查单 / `settleFunding()`；策略、执行、风控都只认它 |
| `RealExchangeGateway` | 实盘与官方模拟盘的实现（转发现有 `BitgetPrivateClient`） |
| `MockExchangeGateway` | 自建 mock：本地账本（现金 + 现货 + 永续空头）、模拟撮合、拒单规则、资金费结算 |
| `MatchEngine` | 按真实盘口逐档撮合：算成交均价与滑点；限价 FOK 吃不满整笔撤销，市价单允许部分成交 |

**与实盘一致的纪律**（有意保留）：clientOid 幂等（重放不重复成交）、下单后必须反查实际成交量、
交易对规则（精度 / 最小量 / 乘数）校验、资金与保证金不足直接拒单。

**有意的简化**（方向都是"宁可少算，也不多算收益"）：

1. 平仓方向（卖现货 / 买回永续）数量超过持仓时按"减到零"处理并打 WARN，实盘会直接拒单——
   这样正常轮动不会因为一位小数误差被误判成"只平了一条腿"；
2. 开空仓的保证金按"1 倍可用担保"粗算（担保 = 现金 + 折扣率 × 现货市值 + 空头浮盈亏），
   不做逐档保证金计算；维持保证金率用配置的固定值 `simulation.maintenance-margin-rate`（默认 2%）；
3. 资金费名义值用结算时刻的真实最新价近似（不落 K 线）；
4. 结算点数据来自 `funding_rate_history`（采集间隔 6 小时），**若在结算点刚过就平仓，可能漏记最后一段资金费**——
   这属于"少算收益"，模块 8 用交易所真实流水核对时会暴露出来。

**账本与查询**：

- 模拟账户现金存 `mock_account`、模拟持仓存 `mock_position`：**重启后接着上一次的仓位继续跑**；
- 订单与成交存 `trade_order` / `trade_fill`（`source=mock`），含滑点与手续费原始值；
- 资金费存 `funding_income`（`source=mock`），唯一键 `(source, symbol, settlement_time)` 保证一个结算点只入账一次；
- 模拟净值每小时写一条 `account_balance_snapshot`（`source=mock`），这是净值曲线与滚动年化的数据源；
- 只读接口：`GET /api/admin/simulation/status`（现金 / 净值 / 持仓 / 累计资金费 / 手续费 / 滚动年化）、
  `GET /api/admin/simulation/equity-curve`（净值曲线）；调试用 POST `/snapshot`、`/settle-funding`。

**首次实测（2026-09-24，`initial-usdt=10000`）**：

| 项目 | 结果 |
| --- | --- |
| 建仓 | 42 币候选池选出 3 个（FARTCOIN / ZRO / PUMP），现货买 + 永续空都按真实盘口成交；滑点 0.02%~0.15%，手续费合计 8.36 USDT |
| 重启接管 | 重启后自动恢复 3 组模拟持仓与现金，按"交易所为准"原则接管 |
| 资金费 | 按真实结算点入账：3 币 × 6 个结算点 = 2.58 USDT/天，对应名义 8.6k → 折算年化约 11%，与回测结论（11.71%）同量级 |
| 开仓成本 | 约 0.25%（手续费 + 现货/合约基差，与 5.1 的滑点实测口径一致） |

**注意**：`strategy.entry-net` 当前仍是 0.04（为官方模拟盘临时调低的值），上真钱前要改回 0.05。
