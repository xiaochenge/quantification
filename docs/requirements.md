# 需求设计（Requirements）

> 状态：需求设计阶段（进行中）。本文档是后续开发的唯一需求依据，模块细节会逐轮补全，代码必须与本文档保持一致。
> 最后更新：2026-09-22

## 1. 目标与边界

- 目标：资金费率套现，**理想总体年化 8%**（弹性目标，非保底；底线是"宁可空仓，也不亏钱"）。
- 交易所：仅 Bitget 一家。
- 策略形态：同时监控多个主流币种，对费率处于高位的币种建立 delta 中性仓位（现货多 + 永续空对冲）吃资金费，并按费率变化动态调仓。具体开平仓与调仓规则待细化。
- 阶段：一期只做"数据接入 + 费率分析 + 模拟交易"，至少 3 个月不使用真实资金；等收益与系统都稳定后再实盘。

## 2. 一期范围（Phase 1）

- 接入 Bitget API，拉取历史资金费率并入库；后台展示；程序内部可读取用于分析。
- 计算每个币种的综合年化，识别"稳定高费"币种。
- 维护监控篮子（候选币种见第 4 节）。
- 模拟交易：不真实下单，用查询到的历史资金费率、资金费结算 / 到账、手续费数据做 mock，跑数月评估收益与稳定性。
- 管理后台：只读展示资金、持仓、盈亏、费率、成本明细等（界面待数据模型确认后再定义）。

## 3. 已确认的业务规则

### 3.1 稳定高费识别

- 只有"最近 10 天资金费率稳定在某个水平"才判定该币费率"稳定高"；单日冲高不作为调仓依据，避免噪声。
- **年化收益计算口径（已确认）**：正费率、负费率都要累加，按净额计算收益，不能只挑正费率。
- **结算周期因币种而异（已确认）**：Bitget 各币的结算周期可能是 1 / 2 / 4 / 8 小时，年化计算与采集调度都要按每个币的实际周期。实测（2026-09-22，351 个币）：**4 小时 266 个、8 小时 84 个、1 小时 1 个**——4 小时才是主流。
- 后台需能查看某个币种最近一段时间的年化收益率。
- **后台默认展示口径（已确认）**：展示"含手续费损耗"的净值年化，另提供"纯资金费"口径作对照。
- **费率恢复过滤（已确认）**：建仓前还要看该币的历史波动——要求"当前连续为正的结算轮数 > 该币历史从负费率恢复到正费率的平均轮数"。回测显示它能在不牺牲分散度的前提下小幅提升收益。
- 待细化：稳定窗口的度量方式（均值 / 中位数 / 方差）、"高"的阈值，以及退出判定。

### 3.2 成本模型

- 现货腿与永续腿的手续费、滑点、买卖价差，全部计入成本。
- 交易所手续费率有查询接口（待用户提供），程序按真实费率核算，而非写死。
- 调仓必须满足：费率差 > 换仓成本 + 安全垫，才触发；用滞回避免频繁来回调仓。
- **换仓成本口径（已确认）**：按"平均 45 天切换一次币种"估算。每次切换 = 平掉旧仓（现货卖出 + 合约买回）+ 建立新仓（现货买入 + 合约卖出）= 2 笔现货吃单 + 2 笔合约吃单。
  - 费率取**私有接口 `GET /api/v3/account/all-fee-rate` 返回的账户真实值**（含 VIP 折扣）：现货吃单 **0.06%**、合约吃单 **0.0375%**。
  - 注意：公共接口 `/market/instruments` 给的是**标准值**（合约吃单 0.06%），比账户实际值高，不能用来算成本。
  - 年化成本系数 = 2 × (0.0006 + 0.000375) × 365 / 45 ≈ **1.58%/年**。

### 3.3 模拟（Mock）阶段

- Mock 通过 `ExchangeGateway` 提供一个"假交易所"实现，策略、执行、核算等其余代码与真实路径共用，只替换数据来源与下单落地。
- 用真实历史数据驱动模拟，产出收益报表与稳定性指标，作为是否上实盘的依据。

### 3.4 数据采集节奏（已确认）

- 资金费率：首次回补最近 90 天，之后按每个币的实际结算周期采集。
- 账户权益 / 币种资产 / 持仓快照：每 1 小时一次。
- 行情快照：只在事件时（下单 / 平仓前后）记录，不做定时轮询。
- K 线：不采集、不落库。

## 4. 目标币种池（已确认）

**入选条件（硬性）**：

- Bitget 上同时存在该币的现货交易对与 U 本位永续（`USDT-FUTURES`），否则无法做"现货多 + 永续空"的对冲。
- **24 小时成交额 ≥ 500 万美元**（取合约口径的 24h 成交额）。门槛是配置项 `watch-coin.min-turnover`，可随时改。
- 排除 RWA 与 Reality 股票代币（代币化股票，不适用资金费逻辑）。

**为什么定 500 万**：全市场扫描与回测（见 `docs/data-model.md` 第 11 节、`docs/phase-2-strategy-design.md` 第 4 节）显示：

- 卡在 ≥2000 万时，回测年化只有 **3.7%**，达不到 8% 目标；
- 放宽到 ≥500 万时，回测年化 **11%~22%**，能覆盖目标；
- 净年化 ≥10% 的币大多落在 500 万以下的尾部，那些币滑点风险过大。

所以 500 万是"能达到目标"与"流动性可接受"之间的折中。**滑点尚未纳入成本模型**，这是后续要补的。

**实现方式**：由 `WatchCoinService` 自动同步（启动时 + 每天一次），把两个产品线的交易对取交集后写入 `watch_coin` 表。

**待细化**：是否需要再加盘口价差 / 深度条件；滑点如何量化。

## 5. 模块划分（已确认）

横向关注点（贯穿所有模块，不单列模块）：配置 / 密钥、日志、告警、定时调度。

1. exchange-gateway 交易所接入（SDK 封装 + 自定网关接口，Real / Mock 两个实现）
2. data-model 数据模型与存储（表结构 + Flyway + MyBatis）
3. funding-analysis 费率分析（综合年化、10 天稳定高费识别、篮子维护）
4. strategy 策略与调仓（开平仓、阈值、滞回、仓位）
5. execution 交易执行（下单 / 撤单 / 幂等 / 状态机）
6. risk 风控（保证金、仓位上限、熔断、强平预警）
7. reconciliation 对账与恢复（本地 vs 交易所核对、重启接管持仓）
8. pnl 成本与盈亏核算（手续费 / 滑点 / 价差、资金费收入、净资产曲线）
9. simulation 模拟交易（假交易所，历史回放 + 前瞻模拟）
10. admin 管理后台（只读看板）

讨论顺序（按依赖）：1、2 → 3 → 4、5、6、8 → 7、9 → 10。
