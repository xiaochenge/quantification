# 订单与资金处理最佳实践

> 本项目的**订单操作纪律**。凡涉及下单、撤单、平仓的代码，写之前先读这一份。
> 最后更新：2026-09-23（含本机模拟盘实测踩到的坑）

## 0. 一句话原则

**金融系统里，一次低级错误的代价可能等于几个月的收益。**

1. 任何写操作（下单 / 撤单 / 划转）都要**幂等**：宁可重复检查，不可重复执行；
2. 任何数量 / 价格都要**按交易所规则校验**，不靠"差不多"；
3. 两条腿的操作要保证**要么都对冲、要么都不做**，绝不留单边敞口；
4. 状态判断**以交易所为准**，本地记录只是副本；
5. 出问题时的默认动作是**停止动作 + 告警**，不是"再试一次"。

## 1. 幂等：clientOrderId 是生命线

- 每笔订单必须带**可复现、可推导**的 `clientOid`，例如 `q{策略仓位ID}-{腿}-{批次号}`。
- 为什么必须可复现：**断网、程序重启、请求超时**时，交易所有可能已经受理了订单而本地没收到响应，此时只能靠 `clientOid` 去查"这笔单到底下没下"。
- 官方明确说明：合约减仓单冲突时 `orderId` 会返回 null，**只能靠 `clientOid` 兜底**。
- 因此：**下单前先用 clientOid 查一次订单状态**，确认不存在再下；下单失败时也用同一个 clientOid 去查，而不是换个 ID 重下。
- Bitget 对 `clientOid` 的字符限制：`^[0-9A-Za-z_:#\-+\s]{1,32}$`。

## 2. 订单状态机

不要只记"成功 / 失败"，要按交易所的真实状态机建模：

```
提交中 → live(已创建) → new(已进撮合) → partially_filled → filled(全部成交)
                                     ↘ cancelled(已撤)
                                     ↘ rejected(被拒)
```

- **禁止**把"没收到异常"当作"已成交"；
- 每次状态变化都要落库（`trade_order` 表），并记录来源（本地推断 / 交易所回查）；
- 进入终态（filled / cancelled / rejected）后不允许再改状态。

## 3. 数量与价格必须按交易所规则校验（本机实测踩过的坑）

下单前必须拿到该交易对的规则并**逐项校验**：

| 规则 | 说明 |
| --- | --- |
| `minOrderQty` | 最小下单量，小于直接被拒 |
| `quantityPrecision` / `pricePrecision` | 小数位数，**超位直接被拒** |
| `quantityMultiplier` / `priceMultiplier` | 下单量必须是它们的整数倍 |

**实测案例（2026-09-23）**：

1. 卖出 `0.23329294` BTC 被拒：`40808 参数校验异常 size checkBDScale error value=0.23329294 checkScale=6` —— 现货数量只允许 6 位小数，而账户余额是 8 位；
2. 接着用**四舍五入**得到 `0.233293`，被拒：`25202 余额不足` —— 因为四舍五入后**大于实际余额**；
3. 正确做法：**向下取整（floor）到允许的精度**，再校验 ≥ `minOrderQty`。

**结论：数量一律"向下取整到精度"，绝不四舍五入；卖单尤其危险。**

## 4. 下单前检查清单

每次下单前都要过一遍：

1. 账户可用余额是否足够（买腿看计价币，卖腿看基础币）；
2. 数量是否满足精度、乘数、最小值；
3. 价格是否符合精度与乘数（限价单）；
4. 是否已存在同 `clientOid` 的订单；
5. 当前是否处于熔断 / 暂停状态；
6. 这一笔会不会导致两腿不平衡（见第 5 节）。

## 5. 两条腿的纪律（delta 中性组合）

1. **同时发起**两条腿，把方向暴露压到最短；
2. 用 **IOC 限价单**而不是市价单：要么全成、要么整笔取消，顺带兜住滑点；
   - 实测对比：本轮用市价单开平仓，损耗约为名义的 **0.32%**，高于纯手续费模型的 0.195%，多出来的就是吃价差；
3. **腿差容差 0.5%**，超出先补小腿；
4. **补不齐就把大腿减到对齐** —— 兜底方向永远是减仓，绝不是加仓追平；
5. 某条腿失败时，**立刻市价补上并告警**；
6. 任何时刻发现"只剩一条腿"，都**优先消除裸露敞口**，先保命再复盘。

## 6. 对账与重启接管

- **交易所永远是真相**，本地表只是副本；启动时以及每 5 秒都要比对持仓 / 余额；
- 重启时若发现"交易所有仓位、本地无记录"，**自动接管并记录**，同时发告警邮件；
- 差异分级：
  - 可自动修正（如数量小数位差异）→ 自动修正并留痕；
  - 必须熔断（持仓方向不符、凭空多出一条腿）→ 立即停止开新仓并告警；
- 每次对账结果与差异都要落库，便于事后追溯。

## 7. 限频与重试

- 行情类约 20 次/秒/IP，下单类约 10 次/秒/UID（见 `docs/api-endpoints.md`）；
- 超限返回 HTTP 429，**不要立刻重试**，要指数退避；
- 重试必须**幂等**：用同一个 `clientOid` 先查状态，再决定是否重下；
- 订单数有上限（Bitget：合约 400 单、现货 400 单，跨全部交易对），撤单逻辑要能兜住上限。

## 8. 低级错误清单（逐条对照）

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 数量四舍五入 | 余额不足 / 被拒 | 向下取整到精度 |
| 忽略数量精度 | `checkBDScale` 被拒 | 按 `quantityPrecision` 截断 |
| 市价单不分批 | 吃穿盘口、滑点放大 | 按盘口深度定量，或 IOC 限价 |
| 把"没报错"当成交 | 状态失真、无法对账 | 主动查订单状态 |
| 随机 clientOid | 重启后无法判断是否重复下单 | 可复现的 ID 规则 |
| 先平一腿再开另一腿 | 中间留下单边敞口 | 两条腿同时发起 |
| 加仓追平腿差 | 越追越亏 | 减大腿对齐 |
| 只看本地状态 | 与交易所脱节 | 交易所为准，定时对账 |
| 忘记 posSide | 双向持仓下报错或开错方向 | 双向持仓必须传 posSide |
| 熔断后手工恢复 | 带着未知风险继续跑 | 恢复前先对账 + 人工确认 |
